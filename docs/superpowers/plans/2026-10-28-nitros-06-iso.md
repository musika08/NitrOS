# NitrOS Plan 6: ISO Builder Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `NitrOS.Image`, the engine that takes the user's Windows 11 ISO, applies a selection's `image` actions to a copy of its Windows image, and writes a new ISO, never touching the source. It follows every rule in spec 5.3, resumes an interrupted build, warns and stops safely on battery, and plugs into plan 5's app as the ISO runner with its own source-ISO screen. Then prove it in the test machine: build an ISO from each card, install it unattended with plan 4's scripts, run the health check, and measure it against plan 4's baseline. Max Lean must get through Setup.

**Architecture:** Every Windows touch point sits behind a small interface in `NitrOS.Image.Systems`: offline DISM (`dism.exe /Image:`), offline registry hives (`RegLoadKeyW` under `HKLM`), files inside the mounted image (deleted with backup and restore privileges, never by changing permissions), the read-only source mount, the ISO writer (oscdimg) and the host facts. Each image action type has one handler that applies the action offline, or marks it **Deferred** to a first-boot script when no offline equivalent exists or Windows refuses the offline write. `ImageBuilder` runs a fixed list of steps, saves a `build.json` state file after every step and every action, and resumes from it after a crash, a cancel or a restart. It first clears any mount or hive a crashed run left behind. The app gets an `IsoRunner : IRunner` in `NitrOS.App.Logic` that calls the builder through a small backend interface, exactly like plan 5's `TuneRunner`. Unit tests use fakes for every layer. Everything that mounts an image or loads a hive runs only inside a "builder" test machine made with plan 4's `New-MeasureVm.ps1`.

**Tech Stack:** .NET 10 (SDK 10.0.402), C#, `net10.0-windows10.0.19041.0`. `dism.exe` from the host's `System32` (always `/English`). `RegLoadKeyW`/`RegUnLoadKeyW` and `AdjustTokenPrivileges` by P/Invoke. `oscdimg.exe` downloaded from Microsoft's symbol server and checked against a pinned SHA-256 and a Microsoft Authenticode signature. Windows PowerShell 5.1 with the in-box Hyper-V module for the test-machine scripts, reusing plan 4's module. xUnit v3 as before. WinUI 3 pages as in plan 5 (Windows App SDK 2.5.1), with `Microsoft.Windows.Storage.Pickers` for file choice.

**Spec:** `docs/superpowers/specs/2026-10-24-nitros-design.md` (sections 1, 3, 4.5, 4.6, 5, 5.1, 5.2, 5.3, 6, 8.2, 11). Also `docs/research/tiny11-removals.md`, `docs/research/dism-access-denied.md`, `docs/research/identifier-checks.md`, `docs/research/notes-for-later-plans.md` (Plan 6 section), `docs/superpowers/plans/2026-10-25-nitros-03-tuner.md`, `docs/superpowers/plans/2026-10-28-nitros-04-measure.md` ("Interface for plan 6", Definitions, Tasks 5 and 7) and `docs/superpowers/plans/2026-10-28-nitros-05-app.md` (Task 6, Task 11, "How plans 6 and 7 plug in").

**This is plan 6 of 7.** Plans 1 (Core), 2 (catalog) and 3 (PC tuner) are merged. Plan 4 (measurement VM) provides `New-MeasureVm.ps1`, `Invoke-MeasureRun.ps1`, `NitrOS.Measure` and the baseline. ## Rulings (choices the spec left open)

1. **Image servicing never runs on the owner's PC during this plan.** Mounting registers a DISM mount on the host, loading a hive registers it under `HKLM`, both outlive a crash, and DISM's Appx provider already refuses the elevated admin on this PC (`dism-access-denied.md`; offline appx servicing may hit the same "Software key" open). Shadow Defender could also throw a mount away at restart. So every real mount, hive load, file delete and oscdimg run happens inside a "builder" test machine made with plan 4's `New-MeasureVm.ps1`. On the owner's PC this plan only builds code, runs fake-based tests and read-only checks, and drives Hyper-V through OWNER CHECKPOINT scripts. Building an ISO on the Ally with the finished app is the owner's own choice later (added to the Ally checklist, Task 16).
2. **Servicing method: `dism.exe /Image:` plus `RegLoadKeyW`.** The DISM API (`dismapi.dll` or the `Microsoft.Dism` wrapper) has the same host-version rule, adds a native dependency and a third-party wrapper, and gains nothing; plan 3 already parses `dism.exe /English`. Hives load under `HKLM\NitrOS.Image.<buildId>.<HIVE>`. `RegLoadAppKeyW` is ruled out by its same-security-descriptor rule.
3. **Offline equivalent per action type:**

   | Action type | Offline in the image | Why |
   |---|---|---|
   | `registry.set` | Yes: `HKLM\SOFTWARE\...` → `Windows\System32\config\SOFTWARE`; `HKLM\SYSTEM\CurrentControlSet\...` → `config\SYSTEM` `ControlSet00N` where N is `Select\Current`; `HKCU\...` → `Users\Default\NTUSER.DAT` (every new account copies it) | Documented hive files. A key that refuses a write-open is Deferred, never forced |
   | `registry.delete` | Yes, same mapping | Same |
   | `service.start` | Yes: `ControlSet00N\Services\<name>` `Start` (Boot 0, System 1, Automatic 2, Manual 3, Disabled 4) and `DelayedAutostart` 1 for AutomaticDelayed. Per-user templates have no instances offline, so the template alone is set | Service start types live in the SYSTEM hive |
   | `startup.disable` (`run` only, the validator allows nothing else in image) | Yes: `StartupApproved\Run` (or `Run32` for a 32-bit HKLM entry) value set to `03 00 00 00 00 00 00 00 00 00 00 00` for each matching Run value, in the mapped hive, with plan 3's byte rules | Same values plan 3 writes live |
   | `appx.remove` | Yes: `/Remove-ProvisionedAppxPackage` for every provisioned package whose `DisplayName` matches the name glob | A fresh image has no users, so deprovisioning removes the app |
   | `capability.remove` | Yes: `/Remove-Capability` | |
   | `feature.disable` | Yes: `/Disable-Feature` without `/Remove` (payload kept, so it can be turned back on) | |
   | `package.remove` | Yes: `/Get-Packages`, glob on Package Identity, `/Remove-Package /PackageName:` | |
   | `file.remove` | Yes: environment variables expanded against the image (`%SystemRoot%` → `<mount>\Windows` and so on), deleted with backup and restore privileges, never following a reparse point | Files are owned by TrustedInstaller; privileges avoid any permission change |
   | `task.disable` | **No. Deferred** to the first-boot machine script (`schtasks /Change /TN <path> /DISABLE`) | Task Scheduler keeps task state in undocumented `TaskCache` registry data next to the XML file; editing either alone is undocumented and can corrupt the task |
   | `power.set` | **No. Deferred** (`powercfg /setacvalueindex` and `/setdcvalueindex` on `SCHEME_CURRENT`, alias verified first) | Power scheme storage in the SYSTEM hive is undocumented |
   | `script` | **No. Deferred**, run as Local System at first boot | Running it offline would run it against the host |
   | `program.uninstall`, `power.scheme`, `launch.at-logon` | Not allowed in image (Core's validator) | The handler throws if one appears |
4. **First-boot setup (spec 5.3 "use first-logon setup"):** two scripts written into the image under `Windows\Setup\Scripts\NitrOS\`. `machine.cmd` (Local System or an administrator) holds deferred HKLM writes, task, power and script items; it runs from `SetupComplete.cmd` and, because SetupComplete is skipped on OEM product keys (the Ally ships with one), also from an HKLM `RunOnce` value at the first administrator sign-in. A `machine.done` marker makes the second route a no-op. `user.cmd` holds deferred HKCU writes and runs as each new user from a `RunOnce` value written into the default user hive. No answer file is added to the ISO, so FirstLogonCommands is not used.
5. **No rollback inside the image.** The image is a new file the user can rebuild, so a failed action does not undo the rest of its switch; the switch is reported PartlyApplied or Failed with the detail. Deferred counts as applied.
6. **One edition out.** The new ISO carries only the chosen edition as `sources\install.wim` (maximum compression). Default choice: the image whose EditionId is `Professional`, else index 1. x64 only; version below 10.0.26100 refused (same as plan 4). `boot.wim` is never changed, no answer file is added and Setup's command line is never touched, so the ISO uses Microsoft's modern Setup exactly as shipped (the Tiny11 "cannot read ProductKey" error came from Core ISOs that changed both).
7. **Host DISM check:** before any build, refuse when the host `dism.exe` file version's build is below 26100. After mounting and before any change, refuse when the host DISM build is below the build of the image's highest `Windows\servicing\Version\<version>` folder (fallback: the `/Get-ImageInfo` version). The refusal unmounts with `/Discard`.
8. **Never write over anything.** The source is opened read-only (an `.iso` is mounted with `Mount-DiskImage -Access ReadOnly`; a folder or drive root is only read). The output must not exist, must not be the source, and must not be inside the source. The ISO is written as `<output>.partial` and renamed at the end.
9. **Work folder:** `<root of the output drive>\NitrOS-work-<buildId>` (a drive root, so the path has no spaces, which oscdimg's boot arguments need), NTFS only, at least 30 GB free on that drive. Deleted after a successful build; kept after a failure or stop so the build can resume. "Throw away" deletes it.
10. **oscdimg:** only NitrOS's own copy, downloaded from `msdl.microsoft.com` (redirects allowed only over HTTPS to `msdl.microsoft.com` or a host ending in `.blob.core.windows.net`, at most 5, file at most 2 MB), kept in `%ProgramData%\NitrOS\tools\oscdimg.exe`, and checked before every use: SHA-256 equals the pin and the Authenticode signer contains "Microsoft Corporation". An installed ADK copy is not used, because its hash cannot be pinned ahead of time.
11. **Battery:** `CheckReady` says not ready while a battery-powered device is unplugged (plan 5's seam lists it as a reason). If the charger is pulled during a build, the log says so once; below 20 percent on battery the build stops after the current action with its state saved, and resumes later.
12. **Card ISO numbers go to a report, not `cards.json`.** `cards.json` keeps one number per card (plan 4, Tune mode). The ISO numbers go to `measure/results/<image campaign>/report.md`. Only `recovery-remove`, which is image-only and has no other number, gets its `measured` field, written by the tool.
13. **`IsoRunner` lives in `NitrOS.App.Logic`,** because `IRunner` is there and `NitrOS.Image` must stay free of app types (the CLI uses it too). It calls `NitrOS.Image` through `IIsoBackend`, as `TuneRunner` calls `ITuneBackend`.
14. **`NitrOS.Image` references Core and Live,** and from Live uses only general helpers (`ProcessRunner`, `Glob`, `DismOutcome`, `RegValue`, a new public `Authenticode` wrapper, `IPowerSource`), never Live's handlers or engine.
